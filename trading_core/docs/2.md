Да, мне нравится это направление. И с учётом твоей текущей структуры я бы **последовательно ушёл от `Worker` к `Module`**.

Только небольшая опечатка в списке:

```text
ExecutionWorker   -> ExecutionModule
BookBuilderWorker -> BookBuilderModule
StrategyWorker    -> StrategyModule
RecordingWorker   -> RecordingModule
```

## Почему `Module` здесь лучше

Сейчас твои бывшие `Worker` уже делают больше, чем просто владеют потоком:

* создают и связывают внутренние компоненты;
* владеют доменными объектами;
* имеют lifecycle;
* запускают processing loop;
* скрывают внутреннюю реализацию pipeline.

Например будущий `ExecutionModule` логически будет представлять целый execution subsystem:

```text
ExecutionModule
│
├── OrderManager
├── IExecutionGateway
├── ExecutionReportSource
├── executionQueue
├── Logger
├── Metrics
└── processing thread
```

Поэтому `Worker` действительно становится слишком узким названием.

```text
Application
│
├── Config
│
├── RuntimeContext
│
├── Queues
│
├── MarketDataModule
├── BookBuilderModule
├── StrategyModule
├── ExecutionModule
```

Его задача:

```cpp
class Application final
{

    void stop();

private:
    config::Config config;

    concurrency::ConditionVariableQueue<...> bookUpdateQueue;
```

# Но я бы пошёл ещё на один шаг дальше

Текущий `common::Worker<T>` после переименования модулей я бы тоже начал переосмысливать.

Сейчас, вероятно, модель примерно такая:

```cpp
class ExecutionWorker final: public common::Worker<ExecutionWorker>
```

После:

```cpp
class ExecutionModule final: public common::Worker<ExecutionModule>
```

Это уже выглядит немного странно:

> Module is a Worker.

А `Module` может не иметь собственного thread вообще.

Например в будущем:

```text
RiskModule
MetricsModule
ConfigurationModule
PnLModule
```

могут не иметь processing loop.

Поэтому я бы **не делал `Module` наследником `Worker` концептуально**.

Вместо этого `Module` сам владеет execution thread, если он ему нужен.

Например:

```cpp
class StrategyModule final
{
public:
    void start();
    void stop();

private:
    void run();

    std::jthread thread;
};
```

Или можно вынести механизм управления thread в отдельную composition/helper abstraction, но не называть все модули worker-ами.

# Очень важный архитектурный момент: владение очередями

Твоё предложение:

> Application создает очереди и отдаёт их нужным worker/module

Я считаю **правильным**.

Например:

```text
Application
│
├── bookUpdateQueue
│      │
│      ├── MarketDataModule
│      └── BookBuilderModule
│
├── strategyEventQueue
│      │
│      ├── BookBuilderModule
│      └── StrategyModule
│
├── executionQueue
│      │
│      ├── StrategyModule
│      ├── ExecutionReportSource
│      └── ExecutionModule
│
└── recordingEventQueue
       │
       ├── BookBuilderModule
       └── RecordingModule
```

Это очень хорошая модель.

### Почему

Очередь — это **связь между модулями**, а не внутренняя деталь одного модуля.

Поэтому:

```cpp
Application
```

владеет каналами коммуникации.

А:

```cpp
ModuleA ---> Queue ---> ModuleB
```

получают ссылки на них.

Это позволяет сразу видеть архитектуру системы по composition root.

# Отдельно про `RuntimeContext`

Твоя текущая идея:

```text
common/runtime_context.hpp
```

сюда очень хорошо вписывается.

Я бы пока сделал его минимальным:

```cpp
namespace trading::common
{
    struct RuntimeContext
    {
        metrics::MetricsCollector& metricsCollector;
        logging::Logger& logger;
    };
}
```

И `Application` создаёт глобальные runtime services:

```text
Application
    |
    ├── Logger
    ├── MetricsCollector
    └── RuntimeContext
             |
             +------> MarketDataModule
             |
             +------> BookBuilderModule
             |
             +------> StrategyModule
             |
             +------> ExecutionModule
             |
             +------> RecordingModule
```

А уже каждый модуль сам решает, что ему нужно:

```cpp
class ExecutionModule
{
private:
    metrics::Metrics& metrics;
    logging::Logger& logger;
};
```

То есть:

```cpp
ExecutionModule(..., RuntimeContext& runtimeContext):
    metrics { runtimeContext.metricsCollector.getThreadMetrics() },
    logger { runtimeContext.logger }
{
}
```

Но, как мы недавно обсудили, `getThreadMetrics()` нужно вызывать **из execution thread**, а не в constructor, если module создаётся в `Application` thread.

Поэтому для новой модульной архитектуры я бы сделал так:

```cpp
void ExecutionModule::run()
{
    metrics::Metrics& metrics = runtimeContext.metricsCollector.getThreadMetrics();

    ...
}
```

И передавал `Metrics&` в `process`, либо хранил его как thread-local runtime state.

## Мой итог

Я считаю, что это **сильное улучшение текущей архитектуры**.

Главная идея, которую я бы зафиксировал:

> **`Application` composes Modules. Modules compose domain components. Queues connect Modules.**

То есть:

```text
Application
     |
     +---- Modules
     |
     +---- Runtime services
     |
     +---- Inter-module queues
```

А внутри:

```text
Module
     |
     +---- owns implementation components
     |
     +---- owns its processing lifecycle
     |
     +---- hides internal wiring
```

Это заметно уменьшит хаос в `Application` и позволит добавлять новые subsystems — например `MetricsModule`, `PnLModule`, `RiskModule` — без превращения composition root в огромный список из десятков низкоуровневых объектов.
