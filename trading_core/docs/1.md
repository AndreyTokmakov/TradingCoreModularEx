Да, мне тоже **`Module` нравится больше, чем `Worker`** для новой архитектуры.

И я бы действительно сделал это **системно**, а не оставлял смесь `Worker`, `Source`, `Handler` и новых `Module`.

## Я бы предложил такую модель

### Верхний уровень

```text
Application
    |
    +-- MarketDataModule
    |
    +-- BookBuilderModule
    |
    +-- StrategyModule
    |
    +-- ExecutionModule
    |
    +-- RecordingModule
```

`Application` становится действительно простым **Composition Root + Lifecycle Manager**.

Его задача:

```text
Application
    |
    +-- load Config
    |
    +-- create shared Queues
    |
    +-- create RuntimeContext
    |
    +-- construct Modules
    |
    +-- start Modules
    |
    +-- stop Modules
```

# 1. Переименовать существующие `*Worker` в `*Module`

Например:

```text
MarketDataWorker      -> MarketDataModule
BookBuilderWorker     -> BookBuilderModule
StrategyWorker        -> StrategyModule
ExecutionWorker       -> ExecutionModule
RecordingWorker       -> RecordingModule
```

Но я бы смотрел не только на механическое переименование.

Например текущий `ExecutionWorker`:

```text
ExecutionWorker
    |
    +-- owns execution thread
    +-- reads executionQueue
    +-- processes OrderRequest
    +-- processes ExecutionReport
```

Это уже фактически **ExecutionModule**, а не просто worker.

```cpp
class ExecutionModule final : public common::Worker<ExecutionModule>
```

Хотя следующим шагом я бы, возможно, даже убрал зависимость от:

```cpp
common::Worker<ExecutionModule>
```

Потому что теперь `Module` — это более высокий архитектурный уровень.

Например:

```cpp
class ExecutionModule final
{
public:
    void start();
    void stop();

private:
    void run();
};
```

Внутри:

```text
ExecutionModule
    |
    +-- std::jthread
    |
    +-- OrderManager
    |
    +-- BinanceExecutionGateway
    |
    +-- BinanceExecutionReportSource
    |
    +-- Queue<ExecutionWorkItem>
```

То есть поток становится **implementation detail модуля**.

---

# 2. Добавить модули там, где сейчас их нет

Ты правильно предлагаешь:

> для чего не было Worker-а добавить

Например сейчас у тебя:

```text
BinanceMarketDataSource
    |
    v
MarketDataMessageHandler
    |
    v
BinanceMarketDataParser
    |
    v
bookUpdateQueue
```

Я бы это завернул в:

```text
MarketDataModule
```

## MarketDataModule

```text
MarketDataModule
    |
    +-- BinanceMarketDataSource
    |
    +-- MarketDataMessageHandler
    |
    +-- BinanceMarketDataParser
    |
    +-- bookUpdateQueue&
```

Например:

```cpp
class MarketDataModule final
{
public:
    MarketDataModule(const config::ExchangeConfig& config,
                     concurrency::Queue<market_data::BookUpdates>& bookUpdateQueue,
                     RuntimeContext& runtimeContext);

    void start();
    void stop();

private:
    exchanges::binance::BinanceMarketDataParser parser;
    market_data::MarketDataMessageHandler messageHandler;
    exchanges::binance::BinanceMarketDataSource source;
};
```

И wiring:

```cpp
MarketDataModule::MarketDataModule(
    const config::ExchangeConfig& config,
    concurrency::Queue<market_data::BookUpdates>& bookUpdateQueue,
    RuntimeContext& runtimeContext):
    parser {},
    messageHandler { parser, bookUpdateQueue },
    source { config.marketDataEndpoint }
{
    source.setMessageHandler(messageHandler);
}
```

Теперь `Application` вообще не знает про:

```cpp
BinanceMarketDataParser
MarketDataMessageHandler
```

Это важно.

# 3. BookBuilderModule

Сейчас у тебя примерно:

```text
BookBuilderWorker
    |
    +-- BookBuilder
    +-- BinanceSnapshotProvider
    +-- OrderBook
    +-- MarketEventDispatcher
```

Я бы сделал:

```text
BookBuilderModule
    |
    +-- thread
    |
    +-- SnapshotProvider
    |
    +-- BookBuilder
    |      |
    |      +-- OrderBook
    |      |
    |      +-- MarketEventDispatcher
    |
    +-- bookUpdateQueue&
```

То есть:

```cpp
class BookBuilderModule final
{
public:
    BookBuilderModule(...);

    void start();
    void stop();

private:
    void run();

    market_data::OrderBook orderBook;
    market_data::MarketEventDispatcher marketEventDispatcher;
    market_data::BookBuilder bookBuilder;

    exchanges::binance::BinanceSnapshotProvider snapshotProvider;

    concurrency::Queue<market_data::BookUpdates>& bookUpdateQueue;

    std::jthread thread;
};
```

Таким образом `OrderBook` больше не является глобальной деталью `Application`.

Он принадлежит:

```text
BookBuilderModule
```

что архитектурно намного понятнее.

# 4. StrategyModule

Сейчас:

```text
StrategyWorker
    |
    +-- ImbalanceStrategy
    +-- StrategyExecutor
```

Станет:

```text
StrategyModule
    |
    +-- ImbalanceStrategy
    |
    +-- StrategyExecutor
    |
    +-- strategyEventQueue&
    |
    +-- executionQueue&
```

Например:

```cpp
class StrategyModule final
{
public:
    StrategyModule(...);

    void start();
    void stop();

private:
    void run();

    strategy::ImbalanceStrategy strategy;
    strategy::StrategyExecutor executor;

    concurrency::Queue<market_data::MarketEvent>& strategyEventQueue;
};
```

`StrategyExecutor` остаётся внутренней деталью модуля.

# 5. ExecutionModule

Вот здесь новая модель особенно хорошо ложится.

Сейчас у тебя:

```text
Application
    |
    +-- BinanceExecutionGateway
    +-- OrderManager
    +-- ExecutionWorker
    +-- BinanceExecutionReportSource
```

Я бы это собрал:

```text
ExecutionModule
    |
    +-- BinanceExecutionGateway
    |
    +-- OrderManager
    |
    +-- ExecutionReportSource
    |
    +-- executionQueue&
    |
    +-- execution thread
```

То есть:

```cpp
class ExecutionModule final
{
public:
    ExecutionModule(...);

    void start();
    void stop();

private:
    void run();

    exchanges::binance::BinanceExecutionGateway gateway;
    OrderManager orderManager;
    exchanges::binance::BinanceExecutionReportSource reportSource;

    concurrency::Queue<ExecutionWorkItem>& executionQueue;
};
```

Архитектура:

```text
                           Exchange
                              |
                              v
                  BinanceExecutionReportSource
                              |
                              |
                              v
                       executionQueue
                              ^
                              |
                              |
StrategyModule ---- OrderRequest
                              |
                              v
                       ExecutionModule
                              |
                    +---------+---------+
                    |                   |
                    v                   v
              OrderManager           Recorder
                    |
                    v
                 Gateway
                    |
                    v
                 Exchange
```

Именно здесь твоя идея с одной:

```cpp
Queue<ExecutionWorkItem>
```

выглядит естественно.

# 6. RecordingModule

Сейчас:

```text
RecordingWorker
    |
    +-- TradeRecorder
    +-- recordingEventQueue
```

Можно:

```text
RecordingModule
    |
    +-- TradeRecorder
    |
    +-- recordingEventQueue&
```

```cpp
class RecordingModule final
{
public:
    RecordingModule(concurrency::Queue<recording::RecordingEvent>& queue,
                    RuntimeContext& context);

    void start();
    void stop();

private:
    recording::TradeRecorder recorder;
};
```

Но здесь есть один важный момент.

У тебя сейчас `ExecutionWorker` напрямую делает:

```cpp
recorder.record(report);
```

Если мы действительно переходим к модели доменных модулей, я бы дальше подумал над тем, чтобы `ExecutionModule` **не владел ссылкой на `TradeRecorder`**.

Лучше:

```text
ExecutionModule
    |
    +-- ExecutionReport
    |
    +---> Recording Queue
```

И уже:

```text
RecordingModule
    |
    v
TradeRecorder
```

То есть оба типа событий могут попадать в recording pipeline:

```text
MarketEvent
ExecutionReport
```

Например:

```cpp
using RecordingWorkItem = std::variant<
    market_data::MarketEvent,
    execution::ExecutionReport
>;
```

Тогда:

```text
BookBuilderModule / MarketData pipeline
                    |
                    v
              Recording Queue
                    ^
                    |
                    |
             ExecutionModule
```

Это, на мой взгляд, будет чище, чем:

```text
ExecutionModule --> TradeRecorder
```

Но это я бы сделал отдельным шагом, не сейчас.

# 7. `Application` после рефакторинга

В результате хочется прийти примерно к такому:

```cpp
class Application final
{
public:
    explicit Application(const std::filesystem::path& configPath);
    ~Application();

    void start();
    void stop();

private:
    config::Config config;
    RuntimeContext runtimeContext;

    concurrency::ConditionVariableQueue<market_data::BookUpdates> bookUpdateQueue;
    concurrency::ConditionVariableQueue<market_data::MarketEvent> strategyEventQueue;
    concurrency::ConditionVariableQueue<recording::RecordingWorkItem> recordingQueue;
    concurrency::ConditionVariableQueue<execution::ExecutionWorkItem> executionQueue;

    MarketDataModule marketDataModule;
    BookBuilderModule bookBuilderModule;
    StrategyModule strategyModule;
    ExecutionModule executionModule;
    RecordingModule recordingModule;

    bool running { false };
};
```

А constructor `Application` становится примерно:

```cpp
Application::Application(const std::filesystem::path& configPath):
    config { loadConfig(configPath) },
    runtimeContext {
        ...
    },
    bookUpdateQueue {},
    strategyEventQueue {},
    recordingQueue {},
    executionQueue {},
    marketDataModule {
        config,
        bookUpdateQueue,
        runtimeContext
    },
    bookBuilderModule {
        config,
        bookUpdateQueue,
        strategyEventQueue,
        recordingQueue,
        runtimeContext
    },
    strategyModule {
        config,
        strategyEventQueue,
        executionQueue,
        runtimeContext
    },
    executionModule {
        config,
        executionQueue,
        recordingQueue,
        runtimeContext
    },
    recordingModule {
        recordingQueue,
        runtimeContext
    }
{
}
```

А lifecycle:

```cpp
void Application::start()
{
    if (running)
        return;

    marketDataModule.start();
    bookBuilderModule.start();
    strategyModule.start();
    executionModule.start();
    recordingModule.start();

    running = true;
}
```

## Что я считаю главным плюсом твоей идеи

Сейчас `Application` знает **слишком много внутренних деталей**:

```text
Application
    |
    +-- OrderBook
    +-- TradeRecorder
    +-- PositionManager
    +-- RiskManager
    +-- Strategy
    +-- Gateway
    +-- OrderManager
    +-- StrategyExecutor
    +-- ExecutionReportSource
    +-- MarketEventDispatcher
    +-- BookBuilder
    +-- SnapshotProvider
    +-- Parser
    +-- Handler
    +-- Source
```

То есть это уже практически весь граф системы.

После рефакторинга:

```text
Application
    |
    +-- Queues
    |
    +-- RuntimeContext
    |
    +-- MarketDataModule
    +-- BookBuilderModule
    +-- StrategyModule
    +-- ExecutionModule
    +-- RecordingModule
```

А внутренности скрыты:

```text
Application
    |
    +---- ExecutionModule
    |          |
    |          +-- Gateway
    |          +-- OrderManager
    |          +-- ReportSource
    |
    +---- StrategyModule
    |          |
    |          +-- Strategy
    |          +-- Executor
    |
    +---- BookBuilderModule
               |
               +-- SnapshotProvider
               +-- OrderBook
               +-- BookBuilder
               +-- Dispatcher
```

Это, IMO, **существенно более масштабируемая архитектура**.

### Моя рекомендация по следующему шагу

Я бы сейчас **не стал переименовывать все файлы одним огромным коммитом**.

Лучше последовательно:

1. `ExecutionWorker` → `ExecutionModule`
2. Собрать внутрь него `OrderManager`, `Gateway`, `ExecutionReportSource`
3. Создать `StrategyModule`
4. Создать `BookBuilderModule`
5. Создать `MarketDataModule`
6. Создать `RecordingModule`
7. В конце упростить `Application`

Так будет проще контролировать зависимости и после каждого этапа собирать/тестировать проект.

И да — я считаю, что направление **`Worker` → `Module`** для твоего проекта сейчас правильное: у тебя эти сущности уже давно делают больше, чем просто читают очередь в отдельном потоке.
