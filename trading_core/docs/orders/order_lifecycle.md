# Order Types и их обработка в HFT Order Management System (OMS)

В контексте HFT (High-Frequency Trading) Order Management System (OMS) — это один из ключевых компонентов торговой инфраструктуры.

OMS отвечает за жизненный цикл ордера: от момента, когда торговая стратегия принимает решение о покупке или продаже, до подтверждения исполнения, отмены или отклонения ордера биржей.

Чтобы разобраться в OMS, важно понимать три вещи:

1. **Order Types** — какие типы ордеров существуют и чем они отличаются.
2. **Order Lifecycle** — какие состояния проходит ордер и как меняются эти состояния.
3. **Order Processing** — как OMS взаимодействует со стратегиями, Risk Management и биржей.

Разберём это с точки зрения C++ HFT-инфраструктуры, уделяя внимание архитектуре и Low-Latency.

---

# 1. Основные типы ордеров (Order Types)

Начнём с наиболее распространённых типов.

## 1.1. Market Order

**Market Order** — ордер на покупку или продажу по лучшей доступной рыночной цене.

Например, стратегия хочет купить 10 BTC.

Она отправляет:

```cpp
Order {
    side     = Side::Buy,
    type     = OrderType::Market,
    quantity = 10
};
```

Что происходит:

Допустим, текущий OrderBook:

| Ask Price | Quantity |
|---:|---:|
| 100 100 | 2 |
| 100 200 | 3 |
| 100 300 | 5 |
| 100 400 | 10 |

Market Buy на 10 BTC исполнится следующим образом:

| Price | Filled Quantity |
|---:|---:|
| 100 100 | 2 |
| 100 200 | 3 |
| 100 300 | 5 |

Средняя цена исполнения:

`(2 × 100100 + 3 × 100200 + 5 × 100300) / 10 = 100230`

Особенности:

- Гарантируется исполнение (если достаточно ликвидности и биржа принимает ордер).
- Цена исполнения не гарантируется.
- Возможен значительный Slippage.
- Может быть исполнен по нескольким ценовым уровням.

В HFT Market Orders используются осторожно, поскольку они могут существенно влиять на рыночную цену.

Кроме того, некоторые биржи реализуют Market Order через IOC Limit Order с защитным ценовым ограничением.

## 1.2. Limit Order

**Limit Order** — ордер с ограничением максимальной цены покупки или минимальной цены продажи.

Например:

```cpp
Order {
    side     = Side::Buy,
    type     = OrderType::Limit,
    price    = 100'000,
    quantity = 10
};
```

Это означает:

> Купить 10 BTC по цене не выше 100 000.

Для Sell:

> Продать 10 BTC по цене не ниже 100 000.

Возможные сценарии:

**Сценарий A:**

Best Ask = 100 100.

Наш Buy Limit = 100 000.

Ордер не исполняется, а попадает в OrderBook.

**Сценарий B:**

Best Ask = 99 900.

Наш Buy Limit = 100 000.

Ордер может быть исполнен немедленно по доступным ценам, не превышающим 100 000.

**Сценарий C:**

Ликвидности недостаточно.

Часть ордера исполняется, остаток размещается в OrderBook (если применён TIF GTC).

Особенности:

- Цена исполнения ограничена.
- Полное исполнение не гарантируется.
- Может оставаться в OrderBook.
- Может исполняться частями (Partial Fill).

Limit Order — один из наиболее важных типов ордеров в HFT.

## 1.3. Stop Order

**Stop Order** — ордер, который активируется при достижении определённой цены (Stop Price).

Например:

```cpp
Order {
    side      = Side::Sell,
    type      = OrderType::Stop,
    stopPrice = 95'000,
    quantity  = 10
};
```

Если цена BTC опускается до 95 000, ордер активируется.

После активации он может превратиться в:

- Market Order — Stop Market.
- Limit Order — Stop Limit.

Здесь важно различать:

- Stop Price — цена активации.
- Limit Price — цена исполнения для Stop Limit.

Пример Stop Limit:

```cpp
Order {
    side      = Side::Sell,
    type      = OrderType::StopLimit,
    stopPrice = 95'000,
    price     = 94'900,
    quantity  = 10
};
```

При достижении 95 000 биржа активирует Limit Sell на 94 900.

Важный момент: Stop Order не обязательно исполняется по Stop Price. Это только условие активации.

В зависимости от биржи Stop Orders могут храниться на стороне биржи или реализовываться самим OMS/алгоритмическим движком.

## 1.4. Iceberg Order

**Iceberg Order** — большой ордер, у которого только часть общего объёма видна рынку.

Например:

```cpp
Order {
    side          = Side::Buy,
    type          = OrderType::Iceberg,
    price         = 100'000,
    quantity      = 100,
    visibleAmount = 5
};
```

Общий объём: 100 BTC.

В OrderBook отображается только 5 BTC.

Когда видимая часть исполняется, выставляется следующая порция.

Зачем это нужно:

- Скрытие реального объёма.
- Снижение Market Impact.
- Снижение вероятности раскрытия торгового интереса.

Iceberg часто реализуется не как отдельный биржевой Order Type, а как алгоритмическая логика OMS.

## 1.5. Pegged Order

**Pegged Order** — ордер, цена которого привязана к определённому рыночному ориентиру.

Например:

- Best Bid.
- Best Ask.
- Mid Price.
- Primary Market Price.

Допустим:

```text
Best Bid = 100 000
Best Ask = 100 100
```

Mid Price:

```text
100 050
```

Pegged Buy может автоматически поддерживать цену около Mid Price.

При изменении рыночной ситуации OMS пересчитывает цену и при необходимости отправляет Cancel/Replace.

В HFT это особенно интересно, поскольку требует быстрой реакции на изменения OrderBook.

## 1.6. Trailing Stop

**Trailing Stop** — Stop Order, у которого Stop Price автоматически перемещается вслед за благоприятным изменением рыночной цены.

Например, Trailing Sell с расстоянием 1 000:

```text
Initial Price = 100 000
Stop Price    = 99 000
```

Если цена повышается до 105 000:

```text
Stop Price = 104 000
```

Если цена начинает снижаться, Stop Price остаётся на прежнем максимальном значении.

При достижении Stop Price ордер активируется.

Обычно используется для автоматического управления риском и фиксации прибыли.

# 2. Time in Force (TIF)

Это отдельная, но крайне важная характеристика ордера.

TIF определяет, как долго ордер может находиться активным и что делать с неисполненным остатком.

Основные варианты:

| TIF | Значение |
|---|---|
| GTC | Good Till Cancelled |
| IOC | Immediate Or Cancel |
| FOK | Fill Or Kill |
| GTD | Good Till Date |
| DAY | До окончания торговой сессии |

### GTC — Good Till Cancelled

Ордер остаётся активным до тех пор, пока:

- Не будет полностью исполнен.
- Не будет отменён.
- Не будет отменён биржей.
- Не истечёт срок действия, установленный биржей.

### IOC — Immediate Or Cancel

Ордер исполняется немедленно в доступном объёме.

Неисполненный остаток отменяется.

Пример:

```text
Order Quantity = 10

Available Liquidity = 6
```

Результат:

```text
Filled   = 6
Cancelled = 4
```

IOC особенно полезен в HFT, когда стратегия не хочет оставлять ордер в OrderBook.

### FOK — Fill Or Kill

Ордер должен быть исполнен полностью немедленно.

Если доступно недостаточно ликвидности, весь ордер отменяется.

```text
Order Quantity = 10
Available Liquidity = 6
```

Результат:

```text
Filled    = 0
Cancelled = 10
```

### GTD — Good Till Date

Ордер действует до конкретной даты и времени.

После истечения срока биржа отменяет его.

# 3. Дополнительные Execution Instructions

Помимо типа ордера и TIF, существуют дополнительные инструкции, определяющие поведение ордера.

| Instruction | Назначение |
|---|---|
| Post Only | Не допускать немедленного исполнения |
| Reduce Only | Только уменьшать существующую позицию |
| Hidden | Не отображать объём в публичном OrderBook |
| Display Quantity | Показывать только часть объёма |
| Self Trade Prevention | Не допускать исполнения собственных ордеров друг против друга |

Особенно интересны следующие.

### Post Only

Допустим:

```text
Best Bid = 100 000
Best Ask = 100 100
```

Мы отправляем:

```text
Buy Limit = 100 100
Post Only = true
```

Обычный Limit Order исполнился бы немедленно против Best Ask.

Но Post Only запрещает немедленное исполнение.

Биржа может отклонить ордер или отменить его в зависимости от своих правил.

Это полезно для Market Making, когда стратегия хочет добавлять ликвидность, а не забирать её.

### Reduce Only

Особенно актуально для Futures и Perpetual Contracts.

Допустим:

```text
Current Position = +10 BTC
```

Мы отправляем Sell Reduce Only на 15 BTC.

Ордер не должен увеличить Short Position.

Максимально допустимый объём для закрытия текущей позиции — 10 BTC.

Конкретная реакция на превышение зависит от правил биржи: ордер может быть ограничен, отклонён или обработан специальным образом.

# 4. Order Lifecycle — жизненный цикл ордера

Теперь перейдём к одной из наиболее важных частей OMS.

Ордер — это не просто структура с Price и Quantity.

Это сущность, которая проходит через последовательность состояний.

Типичный жизненный цикл:

```text
                  +-------------+
                  |   CREATED   |
                  +------+------+
                         |
                         v
                  +-------------+
                  |  VALIDATED  |
                  +------+------+
                         |
                         v
                  +-------------+
                  |   PENDING   |
                  +------+------+
                         |
                         v
                  +-------------+
                  |   NEW       |
                  +------+------+
                         |
              +----------+----------+
              |                     |
              v                     v
       +-------------+       +-------------+
       | PARTIALLY   |       |  REJECTED   |
       | FILLED      |       +-------------+
       +------+------+
              |
       +------+------+
       |             |
       v             v
+-------------+ +-------------+
|  FILLED     | |  CANCELLED  |
+-------------+ +-------------+
```

Это упрощённая схема. В реальной системе переходы зависят от exchange protocol и конкретного события.

Разберём состояния.

| State | Значение |
|---|---|
| Created | Ордер создан стратегией |
| Validated | Проверены параметры и ограничения |
| Pending New | Ожидает отправки или подтверждения |
| New | Биржа подтвердила размещение |
| Partially Filled | Исполнена часть объёма |
| Filled | Полностью исполнен |
| Pending Cancel | Ожидает подтверждения отмены |
| Cancelled | Отменён |
| Rejected | Отклонён |
| Expired | Истёк срок действия |

Важный нюанс:

**Отправка Cancel Request не означает, что ордер отменён.**

До получения подтверждения от биржи ордер может продолжать исполняться.

Например:

1. OMS отправляет Cancel Request.
2. Биржа получает запрос.
3. До обработки отмены исполняет оставшийся объём.
4. Биржа отправляет Execution Report с Fill.
5. Затем отправляет подтверждение Cancel либо сообщает, что отмена невозможна.

Поэтому OMS должна корректно обрабатывать гонки между Execution и Cancel.

Это одна из важных задач при разработке надёжной торговой инфраструктуры.

# 5. Order vs Execution — важное различие

В OMS необходимо чётко разделять понятия Order и Execution.

**Order** — торговая инструкция: купить или продать определённое количество актива.

**Execution** — факт исполнения определённого количества ордера.

Например, стратегия отправляет:

```text
Order ID: 1001
Side: Buy
Price: 100 000
Quantity: 10
```

Биржа может прислать три Execution Report:

| Execution ID | Price | Quantity |
|---|---:|---:|
| 5001 | 100 000 | 2 |
| 5002 | 99 900 | 3 |
| 5003 | 99 800 | 5 |

В результате:

```text
Order Quantity = 10
Filled Quantity = 10
Remaining Quantity = 0
Average Price = 99 880
```

При этом у каждого исполнения должен быть собственный идентификатор.

Почему это важно?

Потому что Execution Reports могут приходить:

- Несколько раз для одного ордера.
- С частичным исполнением.
- Одновременно с Cancel Request.
- С задержкой относительно других сообщений.
- Повторно после восстановления соединения или сессии.

OMS должна уметь корректно учитывать каждое исполнение и не учитывать одно и то же исполнение дважды.

Для этого обычно используются:

- `OrderId` — внутренний идентификатор ордера.
- `ClientOrderId` — идентификатор, присвоенный клиентом (ClOrdID в FIX).
- `ExchangeOrderId` — идентификатор ордера на бирже.
- `ExecutionId` — идентификатор конкретного исполнения.

# 6. Cancel и Replace

В торговых системах недостаточно уметь отправлять новые ордера. Необходимо эффективно управлять уже существующими.

Здесь есть две важные операции.

## 6.1. Cancel Order

Стратегия хочет отменить существующий ордер.

```text
Order ID = 1001
```

OMS отправляет Cancel Request.

Но, как мы уже обсуждали, отмена не происходит мгновенно.

Возможны следующие ситуации:

**Сценарий A:**

```text
New Order
    |
    v
Cancel Request
    |
    v
Cancel Confirmed
```

**Сценарий B:**

```text
New Order
    |
    v
Cancel Request
    |
    v
Partial Fill
    |
    v
Cancel Confirmed
```

**Сценарий C:**

```text
New Order
    |
    v
Cancel Request
    |
    v
Order Filled
    |
    v
Cancel Rejected
```

В третьем случае отменять уже нечего.

Поэтому нельзя просто удалить ордер из внутреннего OrderBook OMS сразу после отправки Cancel Request.

Необходимо дождаться результата операции.

## 6.2. Replace Order

Replace — изменение параметров существующего ордера.

Например:

```text
Original:
    Price = 100 000
    Quantity = 10

Replace:
    Price = 100 100
    Quantity = 10
```

Стратегия хочет изменить цену.

В зависимости от биржи и протокола это может реализовываться через:

- Cancel + New.
- Native Order Modification.
- FIX Order Cancel/Replace Request.

Важный момент для HFT:

**Replace не обязательно сохраняет Queue Priority.**

На многих биржах изменение цены приводит к потере позиции в очереди заявок. Изменение количества также может влиять на приоритет, причём правила зависят от биржи.

Поэтому OMS и стратегия должны учитывать не только новую цену, но и потенциальную потерю приоритета.

# 7. Архитектура OMS

Теперь рассмотрим, как всё это объединяется в реальной торговой системе.

Типичная архитектура может выглядеть следующим образом:

```text
                  +-------------------+
                  |   Trading Engine  |
                  +---------+---------+
                            |
                            v
                  +-------------------+
                  |       OMS         |
                  +---------+---------+
                            |
             +--------------+--------------+
             |              |              |
             v              v              v
       +-----------+  +-----------+  +-----------+
       |  Order    |  |   Risk    |  | Execution |
       |  Manager  |  |  Manager  |  |  Manager  |
       +-----------+  +-----------+  +-----------+
                            |
                            v
                  +-------------------+
                  |  Exchange Gateway |
                  +---------+---------+
                            |
                            v
                  +-------------------+
                  |      Exchange     |
                  +-------------------+
```

Это концептуальная схема. В реальной HFT-системе компоненты могут быть объединены или разделены иначе.

Разберём основные части.

## 7.1. Order Manager

Отвечает за жизненный цикл ордера.

Основные задачи:

- Создание ордеров.
- Назначение идентификаторов.
- Отслеживание состояний.
- Управление Cancel/Replace.
- Учёт исполненного и оставшегося количества.

Например:

```cpp
struct Order
{
    uint64_t orderId;
    uint64_t exchangeOrderId;

    uint64_t price;
    uint64_t quantity;
    uint64_t filledQuantity;

    Side side;
    OrderType type;
    OrderStatus status;
    TimeInForce timeInForce;
};
```

Это только упрощённая модель. В production также понадобятся идентификаторы клиента, инструмента, биржи, версии ордера и другие поля.

## 7.2. Risk Manager

Один из важнейших компонентов OMS.

Перед отправкой ордера необходимо проверить, разрешена ли такая операция.

Например:

```text
Maximum Order Quantity = 100
Maximum Position       = 1 000
Maximum Order Value    = 100 000 USD
```

Стратегия отправляет:

```text
Buy 200 BTC
```

Risk Manager должен отклонить такой ордер.

Типичные проверки:

| Check | Назначение |
|---|---|
| Max Order Quantity | Максимальный объём одного ордера |
| Max Position | Максимальная позиция |
| Max Order Value | Максимальная стоимость ордера |
| Max Open Orders | Максимальное количество активных ордеров |
| Price Collar | Допустимый диапазон цены |
| Rate Limit | Ограничение количества запросов |
| Credit Limit | Ограничение доступного капитала |

В HFT Risk Manager должен работать с минимальными задержками.

При этом нельзя жертвовать корректностью ради производительности.

Особенно интересна концепция **Pre-trade Risk Checks** — проверки до отправки ордера на биржу.

Дополнительно используются:

- Kill Switch — экстренное прекращение торговой активности.
- Cancel All — массовая отмена активных ордеров.
- Position Limits — ограничения торговой позиции.
- Fat Finger Protection — защита от ошибочных параметров ордера.

## 7.3. Exchange Gateway

Это компонент, который непосредственно взаимодействует с биржей.

Его задачи:

- Подготовка сообщений.
- Сериализация ордеров.
- Отправка New Order.
- Отправка Cancel Request.
- Отправка Replace Request.
- Получение Execution Reports.
- Обработка Reject.
- Восстановление соединения.

Для взаимодействия могут использоваться:

- FIX Protocol.
- Native Binary Protocol.
- WebSocket API.
- REST API.

В HFT обычно предпочтительнее специализированные native-протоколы или FIX с оптимизированной реализацией.

REST чаще используется для административных операций, получения конфигурации, первоначальных snapshot и других менее чувствительных к задержкам задач.

# 8. FIX Protocol и Order Management

Отдельно стоит поговорить о FIX.

FIX (Financial Information eXchange) — распространённый протокол обмена финансовыми сообщениями.

Он определяет структуру сообщений для управления ордерами и передачи информации об исполнениях.

Несколько важных типов сообщений:

| FIX Message | MsgType | Назначение |
|---|---|---|
| New Order Single | D | Новый ордер |
| Order Cancel Request | F | Отмена ордера |
| Order Cancel/Replace Request | G | Изменение ордера |
| Execution Report | 8 | Состояние ордера / исполнение |
| Order Cancel Reject | 9 | Отказ в отмене |

Например, для создания ордера используется New Order Single.

Упрощённый FIX message:

```text
35=D
11=CLIENT_ORDER_1001
55=BTCUSD
54=1
38=10
40=2
44=100000
59=0
```

Где:

| Tag | Значение |
|---|---|
| 35 | Message Type |
| 11 | ClOrdID |
| 55 | Symbol |
| 54 | Side |
| 38 | Order Quantity |
| 40 | Order Type |
| 44 | Price |
| 59 | Time In Force |

Например:

```text
54=1  -> Buy
54=2  -> Sell

40=1  -> Market
40=2  -> Limit

59=0  -> Day
59=1  -> GTC
59=3  -> IOC
59=4  -> FOK
```

Обрати внимание: FIX — это не просто формат сообщений.

Это целый протокол взаимодействия с определёнными правилами:

- Управление сессиями.
- Sequence Numbers.
- Heartbeats.
- Resend Requests.
- Session Recovery.
- Message Ordering.

Для OMS это особенно важно, поскольку потерянное или повторно полученное сообщение может привести к неправильному состоянию ордера.

# 9. Order Recovery — восстановление состояния ордеров

Это одна из наиболее интересных задач OMS.

Представим ситуацию:

1. OMS отправила ордер на биржу.
2. Биржа приняла ордер.
3. Произошёл Partial Fill.
4. Соединение с биржей оборвалось.
5. OMS перезапустилась.

Теперь возникает вопрос:

**Как OMS узнает, какие ордера реально существуют на бирже и сколько из них уже исполнено?**

Нельзя просто считать, что все ордера, которые были отправлены до отключения, остались в прежнем состоянии.

Необходимо восстановить состояние.

Обычно используются несколько механизмов.

### 9.1. Persistent Order State

OMS сохраняет информацию об ордерах в устойчивом хранилище.

Например:

```text
OrderId
ClientOrderId
ExchangeOrderId
Symbol
Side
Price
Quantity
FilledQuantity
Status
```

Это позволяет восстановить последнее известное состояние после перезапуска.

### 9.2. Execution Reports

OMS получает информацию об исполнениях и восстанавливает фактическую торговую историю.

Важно иметь возможность обнаруживать дубликаты Execution Reports.

### 9.3. Open Orders Reconciliation

После восстановления соединения OMS запрашивает у биржи список активных ордеров.

Сравнивает:

```text
Local Open Orders
        vs
Exchange Open Orders
```

Обнаруживает:

- Ордер существует на бирже, но отсутствует локально.
- Ордер существует локально, но отсутствует на бирже.
- Различаются количества.
- Различаются статусы.

### 9.4. Position Reconciliation

Дополнительно необходимо сверить позиции:

```text
Local Position
        vs
Exchange Position
```

Позиция — это фактический результат исполненных сделок, а не просто сумма отправленных ордеров.

В production OMS Recovery обычно представляет собой отдельный полноценный механизм, а не просто загрузку сохранённых структур из файла.

# 10. Что особенно важно именно в HFT

Теперь перейдём к вопросам, которые непосредственно влияют на архитектуру C++ OMS.

В обычной торговой системе можно позволить себе некоторые дополнительные операции, сетевые запросы и блокировки.

В HFT всё несколько иначе.

## 10.1. Latency

Представим следующий путь ордера:

```text
Trading Strategy
       |
       v
Order Creation
       |
       v
Pre-trade Risk Checks
       |
       v
Order Manager
       |
       v
Exchange Gateway
       |
       v
Network
       |
       v
Exchange
```

Каждый этап добавляет задержку.

Поэтому важно минимизировать:

- Dynamic Memory Allocation.
- Mutex Contention.
- Unnecessary Data Copies.
- Virtual Function Calls в критическом пути, если они не нужны.
- Cache Misses.
- System Calls.
- Context Switching.

В частности, имеет смысл рассмотреть:

- Lock-free / Wait-free очереди там, где это оправдано.
- Pre-allocated memory.
- Object Pools.
- Cache-friendly структуры данных.
- SPSC communication между потоками.
- CPU affinity.
- NUMA awareness.

Но важно понимать: lock-free не всегда быстрее mutex. Необходимо измерять реальные задержки и contention.

## 10.2. Order ID Management

В HFT очень важно эффективно генерировать идентификаторы ордеров.

Например:

```cpp
class OrderIdGenerator
{
public:
    [[nodiscard]]
    uint64_t next() noexcept
    {
        return m_nextId.fetch_add(1, std::memory_order_relaxed);
    }

private:
    std::atomic<uint64_t> m_nextId{1};
};
```

Это простейшая реализация.

Однако для production стоит учитывать:

- Необходимость уникальности после перезапуска.
- Несколько торговых потоков.
- Несколько биржевых соединений.
- Требования бирж к ClientOrderId.
- Возможность использования локальных sequence numbers.

В некоторых архитектурах удобнее выделять отдельные диапазоны ID каждому потоку.

## 10.3. Order State Management

Я бы рекомендовал отдельно продумать модель состояний.

Например:

```cpp
enum class OrderStatus : uint8_t
{
    Created,
    PendingNew,
    New,
    PartiallyFilled,
    PendingCancel,
    PendingReplace,
    Filled,
    Cancelled,
    Rejected,
    Expired
};
```

Но здесь есть архитектурный нюанс.

Не стоит рассматривать OrderStatus как единственный источник информации о состоянии ордера.

Например, полезно отдельно хранить:

```cpp
struct Order
{
    uint64_t orderId;

    uint64_t price;
    uint64_t quantity;

    uint64_t filledQuantity;
    uint64_t leavesQuantity;

    Side side;
    OrderType type;
    TimeInForce timeInForce;
    OrderStatus status;
};
```

При этом:

```text
leavesQuantity = quantity - filledQuantity
```

Но в реальной системе нужно учитывать Cancel/Replace, Bust и Correct Execution, а также особенности биржевого протокола.

# 11. Какие типы ордеров наиболее интересны для HFT?

Не все Order Types одинаково востребованы.

Я бы выделил следующие:

| Order Type / Instruction | Значимость для HFT | Применение |
|---|---|---|
| Limit | Очень высокая | Market Making, Arbitrage |
| Market | Высокая | Taker Strategies |
| IOC | Очень высокая | Arbitrage, Aggressive Execution |
| FOK | Средняя | Atomic-like execution scenarios |
| Post Only | Очень высокая | Market Making |
| Reduce Only | Высокая | Position Management |
| Iceberg | Средняя | Large Order Execution |
| Stop | Средняя | Risk Management |
| Pegged | Высокая | Passive Execution |

Особенно рекомендую хорошо разобраться в комбинациях:

```text
Limit + GTC
Limit + IOC
Limit + FOK
Limit + Post Only
Limit + Reduce Only
```

Это даст хорошее понимание того, как реальные торговые стратегии управляют ликвидностью.

Обрати внимание: Market, Limit и Stop — это типы ордеров. IOC, FOK и GTC — временные инструкции. Post Only и Reduce Only — дополнительные execution instructions.

Их не стоит объединять в один enum `OrderType`.

# 12. Какую архитектуру я бы предложил для C++ OMS

Для изучения и последующей реализации я бы разделил систему на следующие модули:

```text
OMS
 |
 +-- OrderManager
 |    |
 |    +-- Order
 |    +-- OrderState
 |    +-- OrderIdGenerator
 |    +-- OrderRegistry
 |
 +-- ExecutionManager
 |    |
 |    +-- ExecutionReport
```

## Какие структуры данных понадобятся

Я бы начал со следующих типов:

| Structure | Назначение |
|---|---|
| Order | Основная сущность ордера |
| OrderRequest | Запрос на создание ордера |
| CancelRequest | Запрос на отмену |
| ReplaceRequest | Запрос на изменение |
| ExecutionReport | Ответ биржи |
| Trade | Информация об исполнении |
| OrderEvent | Событие изменения состояния |
| Position | Текущая позиция |
| OrderBook | Рыночная глубина |
| OrderRegistry | Хранение активных ордеров |

Особенно важно разделить:

- `OrderRequest` — намерение стратегии.
- `Order` — внутренняя сущность OMS.
- `ExecutionReport` — сообщение от биржи.
- `Trade` — результат исполнения.

Это разные понятия, и смешивать их в одной структуре не стоит.
