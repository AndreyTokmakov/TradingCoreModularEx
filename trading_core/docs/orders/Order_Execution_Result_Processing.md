В твоей архитектуре я бы распределил ответственность между `OMS`, `RestClient Gateway` и `Execution Report Module` следующим образом.

Главная идея: **OMS отправляет торговые команды и управляет жизненным циклом ордеров, REST Gateway отправляет запросы на биржу, а Execution Report Module получает события исполнения через WebSocket и передаёт их в OMS.**

Разберём весь процесс по шагам — от решения стратегии до получения результата.

# 1. Общая архитектура

```text
                    MARKET DATA
                         │
                         ▼
                    BookBuilder
                         │
                         ▼
                      Strategy
                         │
                    OrderRequest
                         ▼
                     RiskEngine
                         │
                  Validated Order
                         ▼
                        OMS
                         │
                 NewOrderCommand
                         ▼
                  REST Gateway
                         │
                    HTTP POST
                         ▼
                      Binance
                         │
             ┌───────────┴────────────┐
             │                        │
       REST Response           User Data Stream
             │                        │
             ▼                        ▼
       REST Gateway         Execution Report Module
             │                        │
             └───────────┬────────────┘
                         ▼
                        OMS
                         │
                Order State Update
                         ▼
                      Strategy
```

Здесь два независимых канала взаимодействия с биржей:

- **REST** — отправка ордеров, отмена и другие команды, а также запросы состояния.
- **User Data Stream (WebSocket)** — получение событий об изменениях состояния ордеров и исполнениях.

Они дополняют друг друга. REST-ответ не заменяет события исполнения, а WebSocket-событие не является ответом на конкретный HTTP-запрос.

# 2. Шаг 1. Strategy решает выставить ордер

Предположим, стратегия решила купить BTC.

Она формирует внутренний запрос:

```cpp
execution::OrderRequest request {
    .instrument = /* BTCUSDT */,
    .side = Side::Buy,
    .type = OrderType::Limit,
    .price = /* 60000 */,
    .quantity = /* 0.010 */
};
```

Это концептуальный пример, названия полей нужно адаптировать к твоим существующим типам.

Далее запрос проходит через `RiskEngine`.

RiskEngine проверяет, например:

- допустимый размер позиции;
- доступный лимит риска;
- максимальный размер ордера;
- допустимость инструмента и параметров.

Если проверка пройдена, RiskEngine передаёт разрешённую команду в OMS.

Если проверка не пройдена, ордер не отправляется.

**Важно:** RiskEngine разрешает или запрещает выставление ордера, но не отслеживает его дальнейшее исполнение.

# 3. Шаг 2. OMS регистрирует ордер

Получив разрешённую команду, OMS создаёт внутреннюю запись ордера.

Например:

```text
Internal Order ID: 1001
Client Order ID:   bot-1001
Instrument:        BTCUSDT
Side:              BUY
Price:             60000
Quantity:          0.010

Status:            PendingNew
Executed Quantity: 0
```

Зачем нужны два идентификатора?

- `Internal Order ID` — внутренний идентификатор, используемый системой.
- `Client Order ID` — идентификатор, который OMS передаёт Binance для последующего сопоставления ордера с ответами и событиями.

У Binance есть собственное поле `orderId`, которое появится в ответах и событиях биржи.

Таким образом, OMS должен уметь сопоставлять три идентификатора, если они используются в разных частях системы.

После создания записи OMS передаёт команду в `REST Gateway`.

Я бы рекомендовал сначала зарегистрировать ордер внутри OMS, а затем инициировать отправку. Так у нас уже существует внутренний объект, к которому можно привязать результат запроса.

# 4. Шаг 3. REST Gateway отправляет ордер

Твой `REST Gateway` использует уже существующий `networking::RestClient`.

Для Binance Spot это запрос:

```http
POST /api/v3/order
```

Среди параметров будут:

```text
symbol=BTCUSDT
side=BUY
type=LIMIT
timeInForce=GTC
quantity=0.010
price=60000
newClientOrderId=bot-1001
timestamp=...
signature=...
```

REST Gateway отвечает за биржевую специфику:

1. Преобразует внутреннюю команду в параметры Binance API.
2. Формирует timestamp и подпись.
3. Добавляет API key.
4. Вызывает `RestClient::asyncRequest()`.
5. Преобразует HTTP-ответ в типизированный результат.
6. Передаёт результат в OMS.

При этом `networking::RestClient` не должен знать ничего об ордерах, стратегиях или Binance-специфичных полях. Его задача — доставить HTTP-запрос и вернуть HTTP-ответ либо транспортную ошибку.

## Что получает OMS от REST?

Например, Binance принял ордер:

```json
{
    "symbol": "BTCUSDT",
    "orderId": 123456,
    "clientOrderId": "bot-1001",
    "status": "NEW",
    "executedQty": "0.000"
}
```

REST Gateway преобразует ответ в нормализованное представление и передаёт его в OMS.

OMS связывает биржевой `orderId = 123456` с внутренним ордером `1001`.

Но здесь есть важный нюанс: **успешный ответ REST означает, что биржа сообщила о результате обработки запроса, а не обязательно что ордер исполнен.**

Если ответ содержит `status = NEW`, ордер принят и находится в книге ордеров биржи.

OMS обновляет запись:

```text
Order ID:          1001
Exchange Order ID: 123456

Status:            New
Executed Quantity: 0
```

Если ответ потерялся или произошла сетевая ошибка, OMS не должен автоматически считать ордер отклонённым. Биржа могла принять его, а клиент мог не получить ответ.

# 5. Шаг 4. Execution Report Module получает события

Теперь рассмотрим второй канал.

Твой `Execution Report Module` как раз и нужен для обработки изменений состояния ордеров, приходящих от биржи.

Для Binance Spot он будет использовать приватный User Data Stream через WebSocket.

Здесь я бы не использовал тот же обработчик, который получает публичные market data events, как единый бизнес-компонент. Транспортный `WebSocketClient` может быть общим, но обработчики и парсеры должны быть разделены.

Например:

```text
networking::WebSocketClient
            │
            ├── Public Market Data Handler
            │        └── Binance Market Data Parser
            │
            └── Private User Data Handler
                     └── Execution Report Module
```

Execution Report Module выполняет следующие действия:

1. Получает исходный JSON.
2. Разбирает событие `executionReport`.
3. Преобразует биржевые поля в общую модель события исполнения.
4. Передаёт событие в OMS.

Например, Binance сообщает, что ордер частично исполнен:

```json
{
    "e": "executionReport",
    "c": "bot-1001",
    "i": 123456,
    "x": "TRADE",
    "X": "PARTIALLY_FILLED",
    "l": "0.004",
    "z": "0.004"
}
```

Здесь:

| Поле Binance | Значение |
|---|---|
| `c` | Client Order ID |
| `i` | Exchange Order ID |
| `x` | Тип события: `TRADE` |
| `X` | Текущее состояние: `PARTIALLY_FILLED` |
| `l` | Количество в последнем исполнении |
| `z` | Суммарное исполненное количество |

Конкретный состав полей зависит от типа события; при реализации парсера нужно ориентироваться на актуальную документацию Binance.

Execution Report Module не должен самостоятельно решать, что делать со стратегией, балансом или риском. Его основная задача — нормализовать событие и доставить его адресату.

# 6. Шаг 5. OMS обновляет состояние ордера

Execution Report Module передаёт OMS внутреннее событие, например:

```cpp
namespace execution
{
    struct OrderUpdate
    {
        ClientOrderId clientOrderId {};
        ExchangeOrderId exchangeOrderId {};
        OrderStatus status { OrderStatus::Unknown };
        Quantity lastExecutedQuantity {};
        Quantity cumulativeExecutedQuantity {};
        Price lastExecutedPrice {};
    };
}
```

Это концептуальная модель. Поля следует согласовать с уже существующими типами `Order`, `ExecutionReport` и `OrderId`.

OMS находит внутренний ордер и обновляет его состояние.

Например, исходный ордер:

```text
Requested Quantity: 0.010 BTC
Executed Quantity:  0.000 BTC
Status:             New
```

После события:

```text
Last Executed Quantity:       0.004 BTC
Cumulative Executed Quantity: 0.004 BTC
```

Состояние становится:

```text
Status:             PartiallyFilled
Executed Quantity:  0.004 BTC
Remaining Quantity: 0.006 BTC
```

Позже может прийти ещё одно событие:

```text
Last Executed Quantity:       0.006 BTC
Cumulative Executed Quantity: 0.010 BTC
```

Теперь:

```text
Status:             Filled
Executed Quantity:  0.010 BTC
Remaining Quantity: 0.000 BTC
```

Здесь есть важная деталь: **не нужно прибавлять `z` к уже исполненному количеству**. В Binance `z` — накопленное исполненное количество. Его можно сохранить как новое значение, учитывая защиту от устаревших или повторных событий.

Для учёта сделок и комиссий дополнительно потребуется обрабатывать идентификаторы исполнений, например `t`, и обеспечивать дедупликацию.

# 7. Шаг 6. OMS уведомляет Strategy и обновляет связанные данные

После обновления ордера OMS может публиковать внутренние события:

```text
OrderAccepted
OrderPartiallyFilled
OrderFilled
OrderCanceled
OrderRejected
```

Strategy может подписаться на них, если исполнение влияет на дальнейшие торговые решения.

Например, при частичном исполнении стратегия может:

- пересчитать текущую позицию;
- изменить целевую позицию;
- решить, нужно ли выставить дополнительный ордер;
- продолжить ждать исполнения остатка.

Но стратегия не должна самостоятельно изменять состояние ордера в OMS.

Также не стоит путать исполнение ордера и изменение позиции. Для точного учёта позиции нужны данные о сделках, а в некоторых случаях — комиссии, торговые издержки и события изменения баланса.

В дальнейшем можно выделить отдельный `Position Manager` или `Portfolio Manager`, который будет получать события исполнений и обновлять позиции.

# 8. Что делать, если REST и WebSocket сообщают разные состояния?

Это один из важнейших вопросов в реализации OMS.

REST-ответ и WebSocket-событие могут прийти в любом порядке.

Например:

```text
1. OMS отправляет ордер.
2. Binance принимает ордер.
3. Binance быстро исполняет ордер.
4. WebSocket сообщает FILLED.
5. REST-ответ с первоначальным статусом NEW приходит позже.
```

Если безусловно применять каждый результат в порядке получения, OMS может ошибочно вернуть `Filled` обратно в `New`.

Поэтому OMS должен не просто копировать последний полученный статус, а **корректно обрабатывать события жизненного цикла ордера**.

Минимально нужно:

- сопоставлять события с внутренним ордером;
- учитывать накопленное исполненное количество;
- не применять устаревшие данные поверх более актуальных;
- дедуплицировать исполнения;
- корректно обрабатывать терминальные состояния;
- иметь процедуру сверки с биржей после потери соединения.

Также нельзя считать любую сетевую ошибку подтверждением того, что ордер не был принят. Для неопределённых результатов требуется сверка по `clientOrderId` или другим доступным идентификаторам.

# 9. Итоговое распределение ответственности

| Компонент | Что делает |
|---|---|
| `Strategy` | Решает, какой ордер нужен |
| `RiskEngine` | Проверяет допустимость ордера |
| `OMS` | Регистрирует ордер, управляет состоянием и публикует внутренние события |
| `REST Gateway` | Преобразует команды в Binance API-запросы и отправляет их |
| `networking::RestClient` | Выполняет HTTP(S)-запросы |
| `Execution Report Module` | Получает и разбирает приватные события исполнения |
| `networking::WebSocketClient` | Обеспечивает WebSocket-транспорт |
| `Binance User Data Stream` | Передаёт биржевые события |
| `Position Manager` (позже) | Учитывает исполнения и пересчитывает позиции |

## В каком порядке я бы реализовывал это у тебя

Поскольку `OMS` и `REST Gateway` у тебя уже есть, а `Execution Report Module` пока пустой, я бы не переписывал архитектуру.

Следующие шаги:

1. **Определить внутренний `OrderUpdate`**, который OMS сможет принимать независимо от биржи.
2. Реализовать приватный Binance WebSocket в `Execution Report Module`, используя существующий `WebSocketClient`.
3. Написать Binance-парсер `executionReport`.
4. Передавать нормализованные события из модуля в OMS.
5. Добавить обработку состояний и дедупликацию исполнений.
6. Проверить сценарии `NEW → PARTIALLY_FILLED → FILLED`, `NEW → CANCELED`, отклонение и потерю соединения.

При этом `Execution Report Module` не должен отправлять ордера. **Он получает информацию о том, что произошло с уже отправленными ордерами, а OMS остаётся центральным владельцем их жизненного цикла.**
